# Benchmarks

Numbers for ATO, Clause Eight's EU personal-data scanner. Runs before 2.0 were published under its former name, pii-eu, and are kept as written in `bench/compare/results`.

Measured on an Apple M-series laptop (12 cores); the per-detector table on 30 October 2026, the speed measurements on 19 October 2026. Re-run with `go run ./bench -lines 30000`. The table below is regenerated by `ATO_UPDATE_GOLDEN=1 go test ./bench`, and CI fails when it no longer matches the code.

## Synthetic corpus: precision and recall, every detector on

This table turns on every detector, including those that are off by default, so each one is measured. The numbers a user gets with the default settings are in [Compared with other scanners](#compared-with-other-scanners); quote those, not these.

`bench/main.go` builds a corpus in memory: one line in three holds a generated, valid identifier (half with a keyword such as `cnp:` or `iban:`, half under a neutral name); the rest is the noise real repositories are full of: IDs, Unix timestamps in seconds and milliseconds, commit hashes, versions, amounts, references, long trace numbers and minified JSON. Every value is generated and belongs to nobody.

"Pattern-only" runs the same candidate patterns without validation, which is roughly what a regex-based scanner does.

What the numbers say:

- **Validation is what keeps the output usable.** With every detector on, precision is 99.1% at the default level against 34.4% for pattern-only matching. Most of the false positives in this table are not noise: a value valid for two identifiers, one of them more likely, is counted under the country it was not generated for (see "Many national numbers share a shape" below). False alarms on noise lines stay at about 10 in 20,000 at the defaults.
- **Low-base detectors trade recall for quiet output.** Bare numbers with one check digit (EGN, LNCh, PESEL, OIB, BSN, the Nordic and Baltic codes), VAT numbers and contact data start at low confidence, so at the default `--min-confidence medium` they are reported only with a nearby keyword or in their usual printed format. Detectors marked "only with a keyword" are never reported without one.
- **Many national numbers share a shape.** An eleven-digit number can be a valid PESEL, OIB, German tax ID and Estonian code at once. Each value is reported once, preferring the detector whose own name is nearby, then the more confident one. When nothing tells them apart (the same confidence and no keyword for either) the finding says "Possibly A or B" and lists the others in `possible`; the table counts it as right when the generated identifier is one of them. Estonian and Lithuanian personal codes use the same format and check, so an unlabelled one is always reported as either; a regex scanner names one, so the pattern-only column ignores `possible`.
- **Personal data without a check digit stays quiet.** Dates of birth, postcodes, licence and plate numbers, health-card numbers and names in name fields are off by default and reported only next to a keyword; each has 100% precision at the default level here. Names were also checked on about 157,000 public files in Go's module cache: every reported name was in a name field.
- **Danish and Swedish personal numbers look alike.** A Danish CPR number (DDMMYY-SSSS) is often a valid Swedish personnummer too. The Danish detector is off by default, so those values are counted under Sweden, which is why `se-personnummer` is at about 94% here.
- **Cards are the noisiest identifier.** A random 16-digit number with a Visa or Mastercard prefix passes the Luhn check one time in ten, so long trace and order numbers look like cards. A word on the same line that usually labels other numbers (trace, order, invoice, transaction) lowers a card one step unless a card keyword is also there, which keeps card precision at the default level near 95%. The same words lower the thirteen-digit Romanian CNP and Slovenian EMŠO, which random thirteen-digit order and request IDs sometimes pass (the CNP about one time in a thousand).

## Real repository: speed and false positives

Go's own source tree (`$(go env GOROOT)/src`, Go 1.26, 150 MB, 10,720 files), measured on 19 October 2026 with the same machine:

| | v0.2.0 (13 detectors) | v0.4.0 (54 detectors) |
|---|---|---|
| Wall time | 13.4 s | 15.4 s |
| Findings at the default level | 5, all email addresses | the same 5 |

Four times the detectors cost 15% more time on real code, because the prefilter skips most detectors on most lines. Synthetic, digit-heavy text slows down more.

The earlier measurement, for v0.2.0:

A shallow clone of [golang/go](https://github.com/golang/go) (231 MB), deleted after the run:

| | |
|---|---|
| Files scanned | 15,321 (787 skipped: binary or over 5 MiB) |
| Wall time | 6.2 s with 12 workers |
| Peak memory | 32 MB |
| Findings at the default level | 6, all email addresses in LICENSE, CONTRIBUTORS and source comments |

The first run on this repository found 34. The run led to three engine fixes in the same pull request: digits that belong to a decimal number (`7.6971174701310497`) are no longer candidates, a leading minus sign counts as part of a number, and a value in a line holding three or more long numbers (tables of seeds or constants) drops one confidence level. Visa is matched at 13 and 16 digits only; 19-digit Visa numbers are rare and random 19-digit constants are common.

What the numbers say:

- **ATO catches more and warns less.** On open-source application code it catches 88.7% of inserted values
  with 99.4% of its warnings real; Presidio catches 54.1% with 19.2% real, scrubadub 16.3% with 38.2%.
- **What changed since 30 October (38.8% caught, 97.8% real):** a test path no longer lowers a value that
  passes its own check (ADR 10); a value that is the whole of a quoted string is raised when the identifier has a
  date and a check digit or a check letter (ADR 11); a value next to other personal fields is raised; a value whose
  own key names another kind of number (phone, postcode, height) is lowered; order and request words lower
  13-digit national numbers (#267, #269, #271, #274).
- **Where Presidio is still ahead, by choice:** emails (Presidio reports every email; most emails in code and
  tests are fake, so ATO reports an email only next to a word such as `email`, and never on a reserved or
  placeholder domain)
  and cards written under names that usually label other numbers (`id`, `ref`, `order`), where a Luhn-valid
  number is more often an ID. Presidio's 780 card alarms on the original code are the other side of that choice.
- **ATO's own alarms** on the original code are 17 lines, mostly placeholder emails on real domains in
  fixtures.
- **Log calls:** ATO follows a value through local variables and copies, string methods, wrappers,
  templates, defaults, structured logs, error trackers and analytics events, and leaves lengths, flags, masked
  values and IDs alone (#265, #275). HoundDog follows variables too, but its free image found nothing in Kotlin,
  PHP, Ruby or TypeScript, or in analytics calls here.
- **Scanning four more open-source applications** (Mastodon, OpenEMR, Medusa, ERPNext) found false alarms that
  are now fixed (#271): findings fell from 1,947 to 1,155, nearly all of the rest emails in documentation and
  tests.
- **Not measured:** HoundDog's paid tier, Presidio with custom recognisers, and real personal data, which no
  benchmark here will ever use.
